# 实时驾驶舱与下播复盘技术方案（V1）

## 1. 页面与状态流程

`live.html` 是统一的实时驾驶舱入口。顶层模式切换为“直播中 / 下播复盘”：直播中读取当前进行中的 session，下播复盘按历史 `session_id` 选择已结束场次。`ended.html` 只作旧链接兼容，转到 `live.html?mode=review`，不再维护第二套页面壳。

下播复盘是异常/机会驱动的工作台：页面将规则生成的复盘项、证据和实际运营事件映射到整场分轨时间轴。运营点击时间点/区间，在同一页下方查看数据、录屏、话术与必要的主播状态，并可全程录音。结束录音后先完成 ASR，再由后端构建复盘证据包并调用 AI 生成临时正文草稿。运营编辑并保存后，草稿转为正式正文。

`review.html` 是已完成复盘的结果页。它按 `review_id` 读取同一份正式运营正文，允许编辑并保存新版本，但不会再次生成。主播复盘报告是另一份角色化 AI 产物。下场任务逐条保存。数据快照默认折叠。

状态建议：`ENDED → REVIEWING → TRANSCRIBING → DRAFT_READY → OFFICIAL_SAVED`。AI 草稿只存在于 `DRAFT_READY` 的临时编辑状态，不建“运营 AI 草稿”长期业务对象。

## 2. 数据来源与追溯

| 数据 | 来源 | 处理方式 |
| --- | --- | --- |
| 场次、主播、运营、商品、价格、赠品 | 直播场次与商品配置 | 后端快照，带更新时间与版本 |
| 曝光、点击、成交、退款 | 数据仓库/订单归因 | 统一商品和场次口径后计算 |
| 投放消耗、付费成交 | 投放平台与订单归因 | 按分钟对齐时间桶 |
| 录屏 | 直播录制服务 | 通过场次与时间范围查询 |
| 复盘录音 | 录音服务 | 保存原文件、时长、创建人 |
| ASR | 转写服务 | 保存原始语句块和时间戳，不覆盖原文 |
| 语速、分贝 | ASR字数/音频信号 | 确定性计算 |
| 情绪辅助识别 | 模型服务 | 保存标签、置信度和模型版本 |
| 正式正文 | 运营确认保存 | 版本化存储，记录编辑人和保存时间 |

所有展示数字应携带 `source_id`、`metric_definition_version`、`calculated_at`。历史比较结果应保存实际选中的场次/讲解 ID，不能只保存“历史平均”文字。

## 3. 异常规则

规则引擎只消费结构化数据，输出 `anomaly_id/type/time_range/product_id/current_value/comparison_value/delta/rule_version/evidence_refs`。

- 开场异常：默认观察开播前 15 分钟，与配置选定的最近 N 场同主播开场比较；满足最低样本量后按偏离阈值触发。
- 付费成交背离：在对齐的分钟序列上识别投放消耗持续上升、付费成交持续下降的连续区间。图表展示原值，不做指数化。
- 商品异常：分别计算曝光点击率、点击成交率、退款率；逐层判断，正常节点弱化，仅展开触发异常的节点。商品异常的硬前提是当前 `商品 × 时间段` 存在有效讲解段（可追溯到录屏与 ASR）。只有挂链、没有讲解段的商品不得生成 CTR/CVR/退款异常。

商品判断粒度不是“整场商品”，而是 `product_id + segment_start + segment_end + is_explained`。同一商品可以先以“挂链未讲解”产生机会/待观察项，后来进入正式讲解后，再对新的讲解段运行商品异常规则；两段必须生成不同 `reviewItem`，不能用商品级布尔值覆盖整场。

阈值、最近 N 场、最低样本量、时间窗口和触发指标均由后台配置，不硬编码在前端。

## 4. 确定性代码负责

代码/规则负责：开场 15 分钟计算、曝光点击率、点击成交率、退款率、历史比较与差值、投放消耗和付费成交分钟序列、双 Y 轴刻度、异常区间、语速、分贝、商品价格、赠品、主图版本、款色、历史场次筛选、比较顺序、商品历史取值、异常阈值、录音保存、正文保存、任务保存以及用户编辑版本。

代码还必须校验：所有事件属于当前分析时间范围，或明确标记为历史场次；不存在的改价、换赠品、换主播等事件不得进入证据包。

## 5. 配置化规则负责

- 开场观察分钟数、最近 N 场、异常阈值、最低样本量。
- 对比时段顺序：同商品同主播 → 同商品其他主播 → 同类型商品同主播 → 其他可用时段。
- 指标与异常类型映射。
- 异常与复盘因素映射：曝光点击看话术/穿搭款色/主图；点击成交看价格/赠品/话术；退款 V1 只看本次商品讲解话术。
- 主播状态二层展开条件，例如各主标签最大差异不超过配置阈值。

## 6. AI 负责与禁止事项

AI 负责：ASR 语句块主标签分类、可选副标签、话术内容总结、两个时段差异概括、情绪辅助识别、复盘录音总结、从录音中抽取已确认结论/机会点/已执行动作/下场动作、生成运营正文草稿、生成主播报告、抽取任务结构。

AI 不得决定或补写：数值、商品、事件时间、是否改价/换赠品/换主播、某用户是否听到某句话、退款用户画像、历史场次数据、异常幅度、负责人和截止时间。`owner` 或 `deadline` 未在录音中明确时必须为 `null`。

## 7. ASR 与话术标签结构

```json
{
  "segment_id": "asr_seg_000128",
  "session_id": "live_20260907_1300",
  "product_id": "89ZP",
  "speaker": "host_xiaofu",
  "start_time": "2026-09-07T17:16:08+08:00",
  "end_time": "2026-09-07T17:16:15+08:00",
  "text": "ASR原话，禁止由LLM改写",
  "primary_tag": "促单",
  "secondary_tags": ["利益点"],
  "tag_model_version": "talk-tag-v1"
}
```

比例只统计 `primary_tag`，因此品牌、面料、场景、利益点、促单、其他合计约 100%。`secondary_tags` 只用于检索。点击“查看原话”按场次、商品、时段和标签查询全部 segment，默认展示前 5 条并允许展开；V1 不做逐句精准跳录屏。

## 8. 运营正文生成链路

后端构建只读“复盘证据包”：场次基础信息、核心业务数据、商品数据、实际可用人群数据、实际存在的短视频/挂链/测试数据、规则异常、运营实际打开的证据、话术分析、主播状态、复盘 ASR 全文、讨论中明确确认的结论和下场动作。

生成服务仅允许引用证据包，输出固定三段：

1. 本场策略与整体表现。
2. 关键数据、机会及当场动作。
3. 下场动作。

服务端对输出中的商品 ID、数值、时间、人员和事件做证据引用校验；未命中证据的句子标记为不可保存并要求人工删除/修正。运营保存后生成 `official_review` 版本，review 页面按 ID 原样读取，不二次生成。

## 9. 主播报告生成链路

输入只保留与主播直接相关的录音结论、话术、展示和状态证据。输出固定为：表现较好的部分、需要调整的部分、讲解状态、下场练习重点。投放、流量、库存等不得归因给主播。讲解状态仅在话术结构接近但业务结果差异明显时重点输出；情绪始终带置信度与辅助声明。

## 10. 下场任务提取

AI 从复盘录音中抽取 `{task, owner, deadline, evidence_segment_ids}`。后端验证 `owner` 必须匹配录音中明确提及的人员且具备系统账号映射；`deadline` 必须有明确日期或业务时间表达。否则字段置空。人工确认后逐条创建任务，正文保存与任务保存分开事务处理，避免默认生成待办。

## 11. V1 明确不支持

- 退款用户性别、年龄、地域、八大人群画像。
- 退款用户 → 看播时间 → 具体话术的关联。
- 声称“退款用户听到某句话”。
- 点击单句 ASR 精准定位录屏。
- AI 自由补充商品、事件、数字、原因、负责人、日期或历史表现。
- 把情绪模型结果作为原因结论。

V1 退款复盘只支持：识别商品退款率异常，并查看该商品本次讲解期间的话术标签及 ASR 原话。

## 12. 后续迭代

在数据链路和权限合规完成后，可迭代：稳定的视频/ASR 时间轴映射、人工标注话术与转化片段、证据引用可视化、正文版本对比、任务回写、阈值配置后台、模型评估集与标签一致性监控。退款人群与话术关联只有在取得合法、准确的用户级观看链路后才评估上线。

## 13. 复盘场景扩展机制

本原型通过统一的 `demoSessions` 配置保留两个演示场次：一个综合主演示场把多类问题按真实时间关系串在同一场直播中；一个“无明显异常场”用于证明系统不会每场都强找问题。综合场聚合多种能力只服务于原型讲解，不代表一场生产直播通常会同时出现这些问题。生产环境没有固定场次模板，也不会提供“演示场次”下拉框。

正式产品的生成链路是：

```text
结构化场次、商品、投放和话术数据
  + 配置化异常/机会规则
  ↓
reviewItems
  ↓
按 category 调用已有复盘组件
  ↓
数据、录屏、话术、必要的主播状态与复盘录音
```

`reviewItem` 的公共结构至少包含：

```json
{
  "id": "review_item_id",
  "type": "anomaly | opportunity | observation | event",
  "category": "opening | paid | product_ctr | product_cvr | refund | opportunity_product | new_product | linked_product_opportunity | linked_product_observation | operation_event",
  "title": "业务可读标题",
  "startTime": "15:56",
  "endTime": "16:24",
  "productId": "8DF0",
  "productName": "8DF0绿色",
  "isExplained": true,
  "displayMode": "explained_product",
  "currentValue": {},
  "compareValue": {},
  "difference": {},
  "detailType": "product",
  "lane": "product",
  "relatedItemIds": [],
  "relatedMetrics": ["productCtr", "productCvr"]
}
```

`category` 仅用于内部路由，前端展示“异常”“机会”和业务语言。机会规则只能输出“值得继续验证”，不得输出“已经证明是爆款”。新品没有历史数据时输出记录型 reviewItem，不计算历史偏离。

商品相关 `displayMode` 只允许：

- `explained_product`：当前 item 对应有效讲解段，可进入商品异常、商品机会或新品首讲复盘，详情允许展示录屏、话术、ASR 与影响因素。
- `linked_only_opportunity`：挂链未讲解，但结构化点击、自然成交或短视频/挂链数据达到机会规则；只能提示增加讲解验证。
- `linked_only_observation`：挂链未讲解且样本不足；只保留轻量观察记录。

后端和前端都必须执行门禁：`type=anomaly && isExplained=false` 为非法数据；挂链未讲解详情禁止请求话术、主播状态和历史讲解录屏。

未来扩展新场景时依次采用：

1. 新增或调整确定性/配置化规则。
2. 新增 `reviewItem.category` 及其证据结构。
3. 优先复用商品漏斗、分钟趋势、影响因素、双录屏、话术、ASR、主播状态等已有组件。
4. 只有现有组件无法表达新的证据关系型时，才评审新增组件。

原型跨页使用按场次隔离的 `qianji.demo.currentSession.v2` 和 `qianji.demo.formalReviews.v2` 模拟存储；生产环境应改为服务端 `session_id/review_id` 查询和版本化保存，不依赖浏览器本地存储。

## 14. Demo 数据一致性门禁

每个 `demoSession` 在构建和测试阶段执行以下门禁：

- `clicks / exposure` 与曝光点击率允许的舍入误差不超过 0.05 个百分点。
- `orders / clicks` 与点击成交率允许的舍入误差不超过 0.05 个百分点。
- `refunds / orders` 与退款率允许的舍入误差不超过 0.05 个百分点。
- 六个主话术标签合计必须为 100%。
- 报告、主播报告、任务、事件、商品和时间只能引用当前 session 配置。
- 业务事件只能从当前 session 的 `events` 读取；没有事件时显示“无已记录事件”，不能自动补写改价、换赠品或换主播。
- 新品比较对象不存在时禁止生成历史差值。
- 退款场禁止出现用户画像或“退款用户听过某话术”的表述。

原型中的演示数据只代表交互和规则样例，不是生产经营事实。生产环境必须以结构化数据源及证据引用校验结果替换。

## 15. 直播中 / 下播复盘统一驾驶舱架构

两个模式共用同一个页面壳、权限上下文和 session 域模型，但数据范围不同：

- “直播中”通过店铺查询唯一的进行中 session，不提供历史场次组合选择；页面读取实时商品、分钟指标、库存、ASR 和告警流。
- “下播复盘”沿用驾驶舱上层已确定的 `shop_id`，页内只按日期查询已结束 session，再选择具体 `session_id`。选中场次同时决定主播、运营、时间、录屏和复盘状态，不允许页内再切换店铺或手工组合人员。
- 两者复用 `session/product/minute_metric/asr_segment/recording/operation_event`。实时阶段用这些数据辅助发现，复盘阶段沿同一场的时间范围回看证据。
- 直播结束后，从该场入口进入可默认打开下播复盘；切回直播中时展示该场最后一份驾驶舱快照，快照可用性由后端数据保留策略决定。

前端的模式切换只改变视图和查询范围，不复制底层数据，也不把两个模式实现为两个业务产品。

### 15.1 Session 与复盘状态机

“直播结束”不等于“复盘完成”。正式数据模型需要分开两组状态：

```json
{
  "liveStatus": "live | ended",
  "reviewStatus": "pending | reviewing | draft_ready | completed"
}
```

- `live + pending`：直播中，不进入下播复盘录音。
- `ended + pending`：已下播、分钟数据/录屏/reviewItems 已准备，但尚未开始正式复盘。页面主操作是“开始复盘录音”。
- `ended + reviewing`：录音进行中；可继续查看时间轴、录屏、ASR 和商品证据，并记录实际打开的 `reviewItem.id`。
- `ended + draft_ready`：录音已结束、ASR 已完成、AI 草稿可编辑，但还没有正式正文。这一阶段不得显示“复盘已完成”。
- `ended + completed`：运营点击“保存复盘正文”后才进入；正式正文、主播报告、录音和任务都通过同一 `session_id/review_id` 读取。

生产环境的状态转换必须由后端接口持久化，前端不能仅根据“已识别异常”或“已完成录音”推断复盘已完成。建议接口对开始录音、结束录音和保存正文使用幂等请求，并保存操作人、时间与版本。

历史场次默认选择最近的 `ended + pending`；只有不存在待复盘场次时，才选最近的 `completed`。日历按日期展示轻量“待复盘/已复盘”标记，场次下拉展示每个 session 的独立复盘状态。

原型中的“重置演示数据”只删除 2026-09-07 场次在 `localStorage` 中的正式正文、任务和浏览记录，不影响内置的 2026-09-10 已复盘历史场次。生产环境不提供该入口。

## 16. 复盘时间轴模型

时间轴不由运营人工维护。它由两层数据叠加构成：第一层是 `minuteMetrics`，用于绘制整场业务趋势；第二层是 `reviewItems / operationEvents`，用于标记异常、机会、待观察、话术状态证据与实际运营事件。两层都使用同一个 `session.start_time + timestamp` 映射到统一 X 轴。

整场分钟趋势只在时间轴顶部绘制一次。复盘详情只消费选中时段的录屏、话术、ASR、商品漏斗和影响因素，不重复渲染相同或局部趋势图。`relatedMetrics` 只提供切换顶部曲线的建议。

历史场次查询模型为 `currentShop -> sessionsByDate[date] -> session_id`。日历状态仅标记“有直播”和“已复盘”；正文、主播报告、录音及单项复盘结论均通过同一 `session_id/review_id` 读取，已保存内容不再调用 AI 重新生成。

```json
{
  "id": "paid_divergence_1632",
  "type": "anomaly | opportunity | observation | event",
  "category": "paid_gmv_divergence",
  "lane": "traffic_paid | product | talk_state | operation",
  "title": "付费消耗上涨，但成交下降",
  "shortTitle": "消耗成交背离",
  "startTime": "16:32",
  "endTime": "16:52",
  "productId": "89ZP",
  "productName": "89ZP黑色",
  "isExplained": true,
  "displayMode": "explained_product",
  "currentValue": {"spend_delta": 0.31},
  "compareValue": {"paid_gmv_delta": -0.18},
  "difference": {},
  "detailType": "paid",
  "relatedItemIds": ["talk_change_1632"],
  "relatedMetrics": ["gmv", "spend"]
}
```

- `startTime === endTime` 表示瞬时事件；否则表示持续时间区间。
- `type=event` 是证据，不计入“异常/机会/待观察”数量。任何事件必须来自结构化操作日志，不得为了填满时间轴自动补写。
- `lane` 只表达业务维度；机会仍在商品轨，通过 `type=opportunity` 表达判断状态，不再设置“机会”轨。`category` 用于规则和内部路由，`detailType` 决定复用哪一套详情组件。
- `relatedItemIds` 必须保存可追溯的规则或时间关联；前端还可将与当前选中项时间相交的项显示为“同时段证据”，但不把相交解释为因果。
- `relatedMetrics` 只提供“查看关联指标”的查看建议。点击复盘项不会自动替换用户当前曲线；用户确认后才切换，且最多同时展示两项。
- 商品类 tooltip 与详情必须展示当前 item 的讲解状态。`isExplained` 属于时间段而不是商品主数据；同一商品在不同时间段可以分别是挂链未讲解与已讲解。
- 业务筛选与状态筛选分开：业务筛选控制流量/投放、商品、话术/状态轨；状态筛选控制异常、机会、待观察。运营事件轨始终保留为上下文。
- 用户点击某项后，当前项、显式关联项及时间相交项联动高亮，下方单一详情区原位刷新。
- 录音期间客户端记录实际打开的 `reviewItem.id`；证据包只纳入已查看项及其可追溯关联证据。

曲线指标选择属于纯查看层，不参与异常识别。即使用户没有勾选商品点击率，规则引擎仍会基于完整分钟/商品数据识别 CTR 异常。双指标只在单位或数量级不同的时候使用左右 Y 轴，始终展示实际业务值，不做指数化或标准化。

未复盘与已复盘历史场次仅是原型数据状态样例，生产环境不存在固定复盘模板。新场景优先通过新增规则和 `reviewItem.category` 复用已有组件；现有详情组件无法表达新的证据关系时，才评审新增组件。
